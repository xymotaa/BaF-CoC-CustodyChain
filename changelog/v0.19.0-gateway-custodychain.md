# v0.19.0 — Gateway HTTP CustodyChain (fatia 3/4)

_2026-10-01_

## O que foi feito

Terceira fatia do plano aprovado em [[v0.16.0]] (1-rede, 2-chaincode,
3-gateway, 4-trocar LedgerFake). Gateway Node.js/Express em
`fabric/gateway/`, expondo HTTP sobre o chaincode escrito em [[v0.18.0]],
para o `.NET` consumir via `HttpClient` na fatia 4.

Dependências (`@grpc/grpc-js`, `@hyperledger/fabric-gateway`, `express`,
`cors`) e o padrão de conexão (gRPC + TLS + identidade via MSP lido do
disco) seguem o modelo genérico visto no repositório do Leandro — ver
nota em [[v0.16.0]] sobre reaproveitar só infraestrutura, não lógica de
domínio. As rotas em si são novas, desenhadas para espelhar
`IServicoLedger`:

| Rota | Chaincode invocado |
|---|---|
| `POST /dids` | `GerarDid` |
| `POST /dids/:did/ativar` | `AtivarDid` |
| `GET /dids/:did` | `ResolverDid` (evaluate) |
| `POST /credenciais/permissao` | `EmitirCredencialPermissao` |
| `POST /credenciais/coc` | `EmitirCredencialCoC` |
| `GET /credenciais/:id/verificar` | `VerificarCredencial` (evaluate) |
| `POST /credenciais/:id/revogar` | `RevogarCredencial` |
| `GET /ativos/:assetId/historico` | `HistoricoRegistro` (evaluate) |
| `GET /saude` | — (healthcheck do próprio gateway) |

## Bug real encontrado e corrigido: decodificação incorreta do retorno do SDK

Todas as rotas falhavam com `Unexpected non-whitespace character after
JSON`. Causa: `contract.evaluateTransaction`/`submitTransaction` do
`@hyperledger/fabric-gateway` retornam um `Uint8Array`, não um `Buffer`
(confirmado com `Buffer.isBuffer(resultado) === false` num script de
depuração isolado). Chamar `.toString()` direto num `Uint8Array` não
decodifica como texto UTF-8 — produz a lista de códigos de byte separados
por vírgula (ex.: `"123,34,100,..."`), que não é JSON válido.

**Correção:** função helper `decodificar(resultadoBruto)` que faz
`Buffer.from(resultadoBruto).toString('utf8')`, usada em todas as rotas
no lugar de `resultado.toString()` direto. Validado: todas as 8 rotas
testadas via `curl` após a correção, incluindo o fluxo completo (gerar
DID → ativar → emitir credencial de permissão → verificar → consultar
histórico).

## Teste realizado

Com a rede e o chaincode já no ar (fatias 1 e 2), o gateway foi iniciado
(`node src/app.js`, porta 3000) e testado via `curl`:

1. `GET /saude` → `{"status":"conectado"}`.
2. `POST /dids` com DID novo → documento criado (`ativo: false`).
3. `POST /dids/:did/ativar` → `ativo: true`.
4. `GET /dids/:did` → confirma estado persistido.
5. `POST /credenciais/permissao` → credencial emitida.
6. `GET /credenciais/:id/verificar` → `{"valido":true,"motivo":null}`
   (DID titular ativo).
7. `GET /ativos/vestigio-001/historico` → retorna os dois eventos CoC já
   gravados na fatia 2, na ordem correta.
