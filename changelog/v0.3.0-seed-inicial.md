# v0.3.0 — Seed inicial (perfis, tipos de vestígio, usuários de teste)

_2026-09-23_

## O que foi feito

`Data/DbSeeder.cs` — popula três tabelas, conforme previsto na Seção 8.5
do documento técnico ("o seed cria os perfis, os tipos de vestígio e os
cinco usuários de teste"). Idempotente: cada bloco só insere se a tabela
estiver vazia.

- **PERFIL** (5 registros) — os cinco perfis do sistema, com `metodo_did`
  seguindo a reconciliação da Seção 6 (Quadro 8): `ADMIN` →
  `did:legal:admin`, `CUSTODIA` → `did:legal:custodian` (extensão da
  dissertação do Rodrigo), `COLETOR` → `did:legal:delegate`, `PERITO` →
  `did:legal:expert`, `EXTERNO` → `did:legal:judge`.
- **TIPO_VESTIGIO** (7 registros) — um por categoria do enum
  (`BALISTICO`, `VEICULO`, `MATERIAL_GENERICO`, `ANEXO_DIGITAL`, `DROGA`,
  `PADRAO_CONFRONTO`, `SUPORTE`), com `exige_hash = true` apenas para
  `ANEXO_DIGITAL` (RN09).
- **INTERVENIENTE** (5 registros) — um usuário de teste por perfil, todos
  `ATIVO`, DID fictício no formato `did:legal:<subgrupo>:teste-001`.

`Program.cs` — em `Development`, aplica migrations pendentes
(`Database.MigrateAsync()`) e roda o seeder no startup, antes do pipeline
HTTP.

## Decisões e por quê

- **`EXTERNO` mapeado para `did:legal:judge`, não para os três
  subgrupos.** O Quadro 8 lista `judge`, `prosecutor`, `lawyer` como
  aproximações possíveis para esse perfil — o campo `metodo_did` de
  `PERFIL` é singular, então escolhi `judge` como representante. Se a
  aplicação precisar diferenciar juiz/promotor/advogado como intervenientes
  distintos mais adiante, isso vira um dado por `Interveniente`
  (`did_emissor`/DID individual), não uma mudança em `PERFIL`.
- **Seed só roda em Development.** Não popular dados de teste em
  produção é comportamento padrão esperado; nada no documento pede o
  contrário.
- **Sem detalhamento de nomes/matrículas no documento técnico** para os
  cinco usuários de teste — os valores usados (nome, matrícula, órgão)
  são fictícios e plausíveis, sem significado especial.

## Validado

- `dotnet build` limpo
- `ASPNETCORE_ENVIRONMENT=Development dotnet run` aplica migrations
  pendentes e roda o seed — confirmado via `SHOW CREATE TABLE` e
  `SELECT` direto no MySQL (5 perfis, 7 tipos de vestígio, 5
  intervenientes, todos com acentuação armazenada corretamente em
  `utf8mb4`)
- Seed é idempotente: rodar a aplicação de novo não duplica os registros
