# v0.12.0 — T-07 Destinação final + IPFS privado (P-01)

_2026-09-23_

## O que foi feito

### Infraestrutura: IPFS privado local (resolve P-01)

`docker-compose.yml` ganhou o serviço `ipfs` (`ipfs/kubo`), API HTTP em
`127.0.0.1:5001`, gateway de leitura em `127.0.0.1:8899` (porta 8080
padrão colidia com outro processo local). Nenhuma porta exposta à rede
P2P pública — o objetivo é armazenamento de conteúdo endereçável para
este projeto, não uma rede distribuída real nesta fase.

`Services/Armazenamento/IServicoArmazenamentoArquivos.cs` — interface
com `ArmazenarAsync`/`RecuperarAsync`, mesmo padrão de abstração do
`IServicoLedger`. `ServicoArmazenamentoIpfs.cs` implementa via
`HttpClient` chamando a API HTTP do Kubo diretamente (`/api/v0/add`,
`/api/v0/cat`) — sem pacote NuGet de cliente IPFS, a API é simples o
bastante para não justificar a dependência.

**`ANEXO.caminho_relativo` reaproveitado para o CID do IPFS.** O campo é
descrito no documento como "Convenção da Seção 13.4" (uma convenção de
pastas de filesystem), mas comporta qualquer string de até 500
caracteres — decisão do usuário foi guardar o CID ali em vez de abrir
uma coluna nova, mantendo o dicionário de dados sem alteração.

### T-07 — Destinação final (`/destinacao-final`)

Duas telas, `DestinacaoFinalController`:

- **`/destinacao-final/solicitar`** (Central de Custódia): formulário
  com vestígio (`Armazenado` ou `Periciado`), tipo (`DESCARTE` ou
  `RESTITUICAO`), DID do magistrado que autorizou, e upload real do
  mandado judicial. O arquivo é hasheado (SHA-256) antes do upload,
  armazenado no IPFS, e o `Anexo` (tipo `AUTORIZACAO`) é criado com o CID
  retornado. `Descarte` fica pendente (`AprovadoPorId = NULL`).
- **`/destinacao-final`** (Administrador): lista as solicitações
  pendentes e aprova/executa. Ao aprovar: vestígio vai para
  `Descartado` (estado final da máquina de estados, tanto para descarte
  quanto restituição — RN11: o registro digital nunca é excluído, só o
  ciclo do objeto físico se encerra), emite a Credencial #7 do Quadro 14
  (encerramento).

## Decisões e por quê

- **IPFS em vez de filesystem local**, por decisão explícita do usuário
  ao ser questionado sobre o trade-off — P-01 do documento de contexto
  estava em aberto ("IPFS privado ou filesystem local"), e o usuário
  escolheu resolver com infraestrutura real agora em vez de adiar.
- **Central de Custódia solicita, Administrador aprova.** RN20 exige
  "ator portador de credencial de magistrado", mas o magistrado não
  precisa ter conta no sistema — ele assina o mandado fisicamente, e o
  `DidMagistrado` é só o identificador textual registrado. A garantia
  real de RN20 vem do anexo (mandado real, hasheado) mais a segregação
  de funções (RN16) entre quem solicita e quem aprova, não de um login
  de magistrado.
- **Vestígios elegíveis: `Armazenado` ou `Periciado`.** O documento não
  lista essa restrição explicitamente, mas ambos os estados representam
  "vestígio sob custódia estável, aguardando decisão final" — os demais
  estados (em trânsito, em perícia ativa) não fazem sentido para
  encerrar a cadeia.

## Validado

- `dotnet build` limpo, 0 erros/avisos (sem migration nova)
- IPFS testado isoladamente via `curl` antes de integrar: upload e
  recuperação de conteúdo por CID, ida e volta idênticos
- Testado em instância isolada (porta 5236) com o IPFS real rodando
- Fluxo completo: Central de Custódia solicita destinação final com
  upload real de arquivo (multipart/form-data) → confirmado no MySQL:
  `ANEXO` com CID real do IPFS, hash SHA-256 correto; conteúdo
  recuperado de volta do IPFS pelo CID e conferido idêntico ao original
  → Administrador (usuário diferente) aprova → vestígio `Descartado`,
  `AprovadoPorId` diferente de `SolicitadoPorId`, Credencial #7 emitida,
  evento `ENCERRAMENTO` no ledger
- **Teste de bloqueio RN16:** mesmo usuário que solicitou tenta aprovar
  sua própria solicitação → recusado, `AprovadoPorId` permanece `NULL`,
  vestígio não avança para `Descartado`
