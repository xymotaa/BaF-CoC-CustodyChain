# v0.18.0 — Chaincode CustodyChain: DIDs e credenciais verificáveis (fatia 2/4)

_2026-10-01_

## O que foi feito

Segunda fatia do plano aprovado em [[v0.16.0]]/[[v0.17.0]] (1-rede,
2-chaincode, 3-gateway, 4-trocar LedgerFake). Chaincode escrito do zero em
`fabric/chaincode/`, cobrindo o contrato `IServicoLedger`
(`src/CustodyChain.Web/Services/Ledger/IServicoLedger.cs`) que o
`LedgerFake` já implementa em memória — ver nota em [[v0.16.0]] sobre por
que a lógica de domínio não vem do repositório do Leandro (ele só tem o
tutorial genérico `asset-transfer-basic`).

Arquivos:
- `fabric/chaincode/package.json` — dependências `fabric-contract-api` e
  `fabric-shim` `~2.5` (mesmas do template Hyperledger, Apache 2.0).
- `fabric/chaincode/index.js` — registro do contrato (padrão
  `fabric-chaincode-node`).
- `fabric/chaincode/lib/custodyChainContract.js` — único contrato,
  `CustodyChainContract extends Contract`, funções:
  - `GerarDid(did, metodoDid)` — cria DID Document (estado inicial
    `ativo: false`).
  - `AtivarDid(did, didEmissor)` — marca `ativo: true`, registra emissor.
  - `ResolverDid(did)` — leitura do DID Document.
  - `EmitirCredencialPermissao(credencialId, did, didEmissor, perfil)` —
    exige que `didEmissor` esteja ativo; grava credencial tipo
    `PERMISSAO`.
  - `EmitirCredencialCoC(credencialId, assetId, evento, did,
    payloadHashSha256)` — grava credencial tipo `COC` e um registro de
    histórico indexado por `assetId` (chave composta
    `HIST + [assetId, txID]`).
  - `VerificarCredencial(credencialId)` — retorna `{valido, motivo}`:
    inválida se não existe, se revogada, ou (para `PERMISSAO`) se o DID
    titular não está ativo.
  - `RevogarCredencial(credencialId)` — marca `revogada: true`.
  - `HistoricoRegistro(assetId)` — `getStateByPartialCompositeKey` sobre
    o prefixo `HIST`, retorna eventos ordenados por `ocorridoEm`.

## Bug real encontrado e corrigido: não-determinismo de timestamp

Primeira tentativa de invocar o chaincode falhou com
`ProposalResponsePayloads do not match` — os dois peers endossantes
(Org1, Org2) geravam payloads diferentes porque o código usava
`new Date().toISOString()` diretamente, que captura o relógio local de
cada peer (não determinístico, viola a regra fundamental de chaincode
Fabric: toda escrita precisa ser reproduzível byte-a-byte em qualquer
peer que endosse a mesma transação).

**Correção:** todos os timestamps gravados no estado agora vêm de
`ctx.stub.getTxTimestamp()` (timestamp do cabeçalho da transação, mesmo
valor em todos os peers), via um helper `_agora(ctx)` na classe do
contrato. Validado: segunda tentativa de deploy (v1.1) e invocação
funcionaram sem erro de mismatch.

## Outro problema de ambiente corrigido: imagem Docker ausente

`peer lifecycle chaincode install` falhou inicialmente com
`failed to resolve reference "docker.io/hyperledger/fabric-nodeenv:3.1"`
— o peer tenta usar essa tag para buildar o container do chaincode
Node.js, mas ela não existe no Docker Hub (só existe `2.5`, compatível).
Contornado localmente com
`docker tag hyperledger/fabric-nodeenv:2.5 hyperledger/fabric-nodeenv:3.1`
— não exigiu alterar nenhum script do fabric-samples. Isso é específico
do ambiente local e pode precisar ser refeito se as imagens Docker forem
limpas (`docker system prune`, nova máquina, etc).

## Teste realizado

Fluxo completo via `peer chaincode invoke/query` na rede subida em
[[v0.17.0]]:

1. `GerarDid("did:legal:admin:teste-001", ...)` → DID criado, `ativo:
   false`.
2. `AtivarDid(...)` → `ativo: true`.
3. `ResolverDid(...)` → confirma estado persistido.
4. `EmitirCredencialPermissao("cred-perm-001", "did:legal:custodian:...",
   "did:legal:admin:teste-001", ...)` → emitida com sucesso (emissor
   ativo).
5. `VerificarCredencial("cred-perm-001")` → `{valido: false, motivo: "DID
   do titular não está ativo."}` — correto, pois o titular nunca foi
   gerado/ativado. Prova que a regra RN17 (credencial revogada/DID
   inativo bloqueia a ação) é verificável no ledger real, não só no
   `LedgerFake`.
6. `EmitirCredencialCoC` chamado duas vezes para o mesmo `assetId`
   (`vestigio-001`, eventos `Coletado` e `EmCustodia`).
7. `HistoricoRegistro("vestigio-001")` → retornou os dois eventos, na
   ordem cronológica correta.
8. `VerificarCredencial("cred-coc-001")` → válida.
9. `RevogarCredencial("cred-coc-001")` → sucesso.
10. `VerificarCredencial("cred-coc-001")` novamente → `{valido: false,
    motivo: "Credencial revogada."}`.

Todos os 10 passos produziram o resultado esperado.
