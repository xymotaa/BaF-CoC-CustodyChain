# v0.59.0 — reconciliação de identidade local e Fabric

## Objetivo

Impedir que o cadastro MySQL declare uma identidade criptográfica como ativa
quando seu DID v2 não existe ou não está ativo no Fabric.

## Implementado

- `Interveniente.SituacaoIdentidadeLedger` separa situação cadastral de
  identidade criptográfica: `ATIVA`, `DESCONHECIDA`, `PENDENTE_ATIVACAO`,
  `AUSENTE_NO_LEDGER` e `INATIVA`.
- O filtro global do `CustodyChainDbContext` só expõe intervenientes com
  identidade ledger ativa aos fluxos operacionais. Autenticação e gestão usam
  `IgnoreQueryFilters` porque validam o DID diretamente no Fabric.
- A gestão administrativa sincroniza um DID e oferece reinscrição somente após
  confirmação de ausência no ledger. A reinscrição reutiliza a inscrição,
  prova de posse e ativação DID v2 existentes; não cria chaves no servidor.
- A migration marca o acervo prévio como `DESCONHECIDA`, exigindo reconciliação
  explícita antes do uso operacional.

## Validação

- Build .NET e 69 testes .NET executados com sucesso.
- Migration aplicada no MySQL local; os registros existentes foram marcados
  como `DESCONHECIDA`.

## Pendente operacional

Cada titular ausente precisa concluir a reinscrição com sua própria wallet e
um administrador ativo deve assinar a ativação. Tokens persistentes dos
gateways continuam configurados fora do repositório.
