# v0.20.0 — IServicoLedger real: troca do LedgerFake pelo Fabric (fatia 4a/4)

_2026-10-01_

## O que foi feito

Última fatia do plano aprovado em [[v0.16.0]] (1-rede, 2-chaincode,
3-gateway, 4-trocar LedgerFake). Nova implementação de `IServicoLedger`:

- `src/CustodyChain.Web/Services/Ledger/ServicoLedgerFabric.cs` — chama o
  gateway HTTP ([[v0.19.0]]) via `HttpClient`, implementando os 7 métodos
  do contrato (`GerarDidAsync`, `AtivarDidAsync`, `ResolverDidAsync`,
  `EmitirCredencialPermissaoAsync`, `EmitirCredencialCoCAsync`,
  `VerificarCredencialAsync`, `HistoricoRegistroAsync`) traduzindo DTOs
  C# ↔ JSON do gateway.
- `Program.cs` — troca de `AddSingleton<IServicoLedger, LedgerFake>()`
  para `AddHttpClient<IServicoLedger, ServicoLedgerFabric>(...)`, mesmo
  padrão já usado para `IServicoArmazenamentoArquivos`/IPFS. URL do
  gateway configurável via `Ledger:GatewayUrl` (default
  `http://127.0.0.1:3000`).
- `LedgerFake.cs` mantido no código (não removido) — útil para rodar a
  aplicação sem precisar subir a rede Fabric completa (ex.: demo rápida,
  desenvolvimento de UI). Trocar entre as duas é só mudar o registro no
  `Program.cs`.

**Escopo explicitamente deixado de fora desta fatia** (decisão do
usuário): o `AuditoriaController` (T-11, linha do tempo e verificador
independente) continua lendo do MySQL diretamente, não do
`IServicoLedger`. Resolver isso de vez — fazendo o verificador consultar
o ledger real via `VerificarCredencialAsync`/`HistoricoRegistroAsync` —
fica para uma fatia futura (5), porque exige mudar a lógica de negócio do
controller, não só a injeção de dependência. A limitação continua
registrada em `changelog/v0.15.1-limitacao-verificador-le-do-banco.md`.

## Teste realizado (ponta a ponta, sistema real)

Com rede Fabric, chaincode e gateway já no ar (fatias 1-3), a aplicação
.NET foi iniciada e testada via fluxo real do sistema (não só chamada
direta ao gateway):

1. Login como `did:legal:admin:teste-001` via `/entrar`.
2. Submissão do formulário "Cadastrar interveniente"
   (`/gestao-perfis/cadastrar`) com perfil Administrador.
3. Log da aplicação confirma a chamada HTTP real:
   `POST http://127.0.0.1:3000/dids` → `201`, levando **~2,2 segundos** —
   bate com a "latência conhecida de ~2,3s por emissão de credencial"
   que o documento técnico já registrava (medida por Loffi). Essa
   latência deixa de ser uma cifra do documento e passa a ser observada
   de verdade neste TCC.
4. Registro `INTERVENIENTE` persistido no MySQL com o DID real retornado
   pelo ledger (`did:legal:admin:fc8c6f4b95434a968a049d8ee404fb0b`).
5. Consulta direta ao gateway (`GET /dids/<did>`) confirma que o mesmo
   DID existe no ledger Fabric, com o estado correto (`ativo: false`,
   coerente com o fluxo de duas etapas GERADO→ATIVO decidido em
   `v0.14.0`).

Esse teste prova a cadeia completa: Razor → Controller → `HttpClient` →
Gateway (gRPC) → Chaincode → Ledger Fabric, com o dado de volta
confirmado tanto no MySQL quanto consultado diretamente no ledger.

## O que isso resolve

O risco R-04 (rede Fabric não testada em Arch Linux) e a arquitetura
descrita na "Decisão que mais importa para o código"
(`docs/CONTEXTO-PROJETO.md`) — "`IServicoLedger` é o único ponto do C#
que conhece o gateway" — deixam de ser teóricos. O sistema inteiro, do
cadastro de interveniente à emissão de credencial de cadeia de custódia,
agora pode rodar sobre uma blockchain permissionada real, não mais um
substituto em memória.

## Próximo passo (fatia 5, não escopo desta sessão)

Reescrever `LinhaDoTempo` e `Verificador` em `AuditoriaController` para
consultar `IServicoLedger.HistoricoRegistroAsync`/`VerificarCredencialAsync`
em vez do `CustodyChainDbContext` direto — isso fecha de vez a limitação
de `v0.15.1`, fazendo o verificador independente da T-11 conferir contra
o ledger de verdade, não mais o MySQL.
