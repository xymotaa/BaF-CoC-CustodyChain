# v0.61.0 — runbook local: tokens, DIDs e testes integrados

## Objetivo e limites

Este roteiro recupera um ambiente local após a reconciliação de identidades:
rotaciona os tokens entre aplicação e gateways, restaura a wallet administrativa,
reinscreve DIDs ausentes com prova de posse e executa testes. Ele não cria chave
privada no servidor, não registra segredo no repositório e não altera o estado
do ledger sem uma assinatura feita pela wallet do titular.

> Execute tudo no computador que custodiará as wallets de desenvolvimento. Não
> cole tokens, senhas, chaves privadas ou códigos de pareamento em chats,
> commits, arquivos dentro do repositório ou capturas de tela.

Espere `custodychain-mysql` e `custodychain-ipfs` saudáveis, os peers

## 1. Rotacionar os tokens dos gateways

Os tokens usados anteriormente devem ser considerados comprometidos se foram
colados em um terminal, chat ou log. Para desenvolvimento local, guarde os
novos valores fora do repositório, com permissões restritas. O arquivo abaixo
é uma conveniência local; em homologação/produção use o gestor de segredos
aprovado pela instituição.

```bash
STATE_DIR="${XDG_STATE_HOME:-$HOME/.local/state}/custodychain"
install -d -m 700 "$STATE_DIR"
umask 077
{
  printf 'export GATEWAY_ORG1_SERVICE_TOKEN=%q\n' "$(openssl rand -base64 48)"
  printf 'export GATEWAY_ORG2_SERVICE_TOKEN=%q\n' "$(openssl rand -base64 48)"
} > "$STATE_DIR/gateway-tokens.sh"
chmod 600 "$STATE_DIR/gateway-tokens.sh"
source "$STATE_DIR/gateway-tokens.sh"
unset STATE_DIR
```

Não mostre o conteúdo de `gateway-tokens.sh`. A rotação só passa a valer
quando os processos dos gateways forem reiniciados com os novos valores.

## 2. Iniciar os gateways Fabric

Abra **dois terminais**, carregue o mesmo arquivo de tokens em ambos e mantenha
os processos abertos. No primeiro, inicie a organização administrativa:

```bash
cd /home/xym/Projetos/BaF-CoC-CustodyChain
source "${XDG_STATE_HOME:-$HOME/.local/state}/custodychain/gateway-tokens.sh"
cd fabric/gateway
GATEWAY_SERVICE_TOKEN="$GATEWAY_ORG1_SERVICE_TOKEN" npm start
```

No segundo, inicie a organização de custódia/perícia:

```bash
cd /home/xym/Projetos/BaF-CoC-CustodyChain
source "${XDG_STATE_HOME:-$HOME/.local/state}/custodychain/gateway-tokens.sh"
cd fabric/gateway
MSP_ID=Org2MSP PORT=3001 PEER_ENDPOINT=localhost:9051 \
PEER_HOST_ALIAS=peer0.org2.example.com \
CRYPTO_PATH="$(pwd)/../network/organizations/peerOrganizations/org2.example.com" \
TLS_CERT_PATH="$(pwd)/../network/organizations/peerOrganizations/org2.example.com/peers/peer0.org2.example.com/tls/ca.crt" \
MSP_PATH="$(pwd)/../network/organizations/peerOrganizations/org2.example.com/users/User1@org2.example.com/msp" \
GATEWAY_SERVICE_TOKEN="$GATEWAY_ORG2_SERVICE_TOKEN" npm start
```

Em um terceiro terminal, confirme somente a disponibilidade e a MSP de cada
processo; este endpoint não exige token:

```bash
curl --fail --silent http://127.0.0.1:3000/saude; echo
curl --fail --silent http://127.0.0.1:3001/saude; echo
```

O resultado deve informar `status: conectado`, com `Org1MSP` e `Org2MSP`,
respectivamente. Se não informar, pare aqui e corrija a conectividade Fabric;
não marque DIDs como ativos no MySQL manualmente.

## 3. Criar e iniciar a wallet administrativa local

No estado local atual não existe `wallet/data/wallet.db`; portanto a chave
administrativa deve ser criada e protegida localmente. Este comando pede a
senha de forma interativa e cria um banco SQLite com permissão de arquivo
restrita, ignorado pelo Git:

```bash
cd /home/xym/Projetos/BaF-CoC-CustodyChain/wallet
npm run create-admin -- --did did:legal:admin:teste-001
```

Guarde a saída pública (`did`, `keyId`, `publicKeyMultibase`) para o passo
seguinte. Não guarde a senha. Antes de migrar ou inicializar o DID, consulte o
ledger usando o token da Org1:

```bash
source "${XDG_STATE_HOME:-$HOME/.local/state}/custodychain/gateway-tokens.sh"
curl --silent --show-error --fail-with-body \
  -H "Authorization: Bearer $GATEWAY_ORG1_SERVICE_TOKEN" \
  'http://127.0.0.1:3000/v2/dids/did%3Alegal%3Aadmin%3Ateste-001'
```

- Se o documento retornado for legado, execute **uma vez** a migração v1 para
  v2, substituindo apenas os dois valores públicos abaixo:

  ```bash
  curl --silent --show-error --fail-with-body \
    -X POST http://127.0.0.1:3000/v2/bootstrap/admin/legacy-migration \
    -H "Authorization: Bearer $GATEWAY_ORG1_SERVICE_TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"did":"did:legal:admin:teste-001","verificationMethodId":"did:legal:admin:teste-001#auth-1","publicKeyMultibase":"<CHAVE_PUBLICA_DA_WALLET>"}'
  ```

- Se receber `404` porque o DID administrativo não existe, use
  `/v2/bootstrap/admin` com o mesmo corpo. Esse bootstrap é único.
- Se o documento já for v2 ativo, não execute bootstrap ou migração; confirme
  que `authentication` e `capabilityInvocation` referenciam `#auth-1`.

Inicie a wallet no mesmo terminal ou em outro terminal local. Ela deve ouvir
somente em `127.0.0.1`; anote o código de pareamento exibido, sem compartilhá-lo:

```bash
cd /home/xym/Projetos/BaF-CoC-CustodyChain/wallet
npm start
```

Validação sem segredo:

```bash
curl --fail --silent http://127.0.0.1:43123/health; echo
```

Em outro terminal, carregue os tokens e passe-os somente por variáveis de
ambiente para o processo .NET. Não acrescente esses valores a `appsettings`.

Abra `http://localhost:5143/entrar`. Entre com o DID administrativo, a senha
da wallet e o código de pareamento. A senha é enviada pelo navegador somente
para `127.0.0.1:43123`.

## 5. Reconciliar e reinscrever os DIDs

No menu **Gestão de perfis**, primeiro clique em **Sincronizar identidade**
para cada titular. O estado local inicial conhecido é `DESCONHECIDA` para os
cinco usuários de teste ativos:

| Perfil | DID | Gateway de escrita |
|---|---|---|
| Administrador | `did:legal:admin:teste-001` | Org1MSP |
| Central de Custódia | `did:legal:custodian:teste-001` | Org2MSP |
| Agente Coletor | `did:legal:delegate:teste-001` | Org1MSP |
| Perito | `did:legal:expert:teste-001` | Org2MSP |
| Órgão externo | `did:legal:judge:teste-001` | conforme política do ledger |

Para cada estado `AUSENTE_NO_LEDGER`:

1. O administrador seleciona **Reinscrever DID**. Copie o DID, `enrollmentId`
   e código de inscrição, pois o código é exibido uma vez e expira em 15
   minutos.
2. No dispositivo do titular, a wallet local cria a identidade e a chave
   Ed25519. A senha do titular nunca é fornecida à aplicação ou ao operador.
   A API local `POST /v1/identities` é a interface disponível para essa criação;
   use um cliente local que não grave corpo de requisição nem senha no histórico.
3. O titular solicita à aplicação o comando de registro em
   `POST /gestao-perfis/inscricoes/{enrollmentId}/comando-registro`, enviando
   `codigoInscricao`, `verificationMethodId` igual a `<DID>#key-1` e a chave
   pública multibase. A aplicação só devolve comando válido enquanto a inscrição
   estiver pendente e dentro do prazo.
4. A wallet do titular assina esse comando em
   `POST /v1/proofs/did-registration`; envie `command` e `signature` para
   `POST /gestao-perfis/inscricoes/{enrollmentId}/prova-registro?codigo=<codigo>`.
   A aplicação publica apenas a prova recebida no Fabric pela organização
   administrativa e a inscrição passa a `REGISTRADA`.
5. O administrador autenticado abre **Ativar com prova** para o titular,
   revisa o DID e usa a própria wallet para assinar a ativação. Somente após a
   confirmação Fabric a aplicação marca a identidade local como `ATIVA`.

Faça uma reinscrição por vez e nunca reutilize comando, código de inscrição,
`commandId` ou assinatura. DIDs revogados não devem ser reinscritos como se
fossem ativos: siga o fluxo de recuperação/revogação apropriado.

## 6. Roteiro de testes

### Pré-testes automatizados

Da raiz do projeto, com os serviços de desenvolvimento em execução:

```bash
dotnet build src/CustodyChain.Web/CustodyChain.Web.csproj --no-restore --nologo
dotnet test tests/CustodyChain.Web.Tests/CustodyChain.Web.Tests.csproj --no-restore --nologo
(cd wallet && npm test)
(cd fabric/gateway && npm test)
git diff --check
```

Registre o resultado real de cada comando. Se o NuGet não puder consultar
metadados de vulnerabilidade, isso é um aviso de rede; não o confunda com
sucesso ou falha dos testes.

### Smoke test de infraestrutura

1. Confirme os três `health checks` dos gateways e wallet.
2. Com um token deliberadamente incorreto, uma rota autenticada do gateway
   deve responder `401`; com o token novo, a mesma consulta de DID deve
   responder `200` ou `404` conforme o estado real do ledger.
3. Pare e reinicie um gateway carregando novamente o arquivo local de tokens;
   o health check deve voltar a informar a mesma MSP. Isso confirma que a
   rotação não depende de um token antigo em memória.

### Teste funcional de identidade

1. Faça login como administrador via prova de posse.
2. Sincronize todos os DIDs e registre o estado resultante em cada linha.
3. Reinscreva um DID ausente completo (reservar, chave do titular, prova de
   registro e ativação administrativa).
4. Saia e faça login com esse novo DID. O login deve falhar antes da ativação
   e funcionar somente depois de o Fabric confirmar a ativação.
5. Tente uma operação de domínio com identidade `DESCONHECIDA`,
   `AUSENTE_NO_LEDGER` ou `INATIVA`: ela deve ser bloqueada antes de criar
   operação/outbox. Repita com identidade `ATIVA` e VC válida quando a política
   da operação exigir VC.

### Teste de integração Fabric e autorização distribuída

Com identidades ativas, crie dados de teste e execute uma operação assinada
apropriada ao perfil (por exemplo, coleta para `COLETOR` ou perícia para
`PERITO`). Verifique no resultado que:

- a wallet solicitou a assinatura local;
- o gateway selecionado corresponde à MSP da política do DID;
- a assinatura, `operationId`, nonce e validade foram aceitos pelo Fabric;
- repetir o mesmo envelope retorna resultado idempotente, enquanto reutilizar
  o mesmo `operationId` com conteúdo diferente é conflito;
- uma assinatura expirada, DID inativo, VC revogada/expirada ou gateway da
  organização errada é rejeitada sem alterar o estado de domínio local.

## Critério de encerramento

O ambiente está pronto para a bateria final somente quando os dois gateways e
a wallet estiverem saudáveis, os tokens antigos não autenticarem, o DID
administrativo v2 estiver ativo, cada DID de teste necessário estiver
reconciliado, e os testes automatizados e funcionais acima tiverem resultado
registrado. Não altere diretamente `SituacaoIdentidadeLedger` ou dados Fabric
para contornar uma prova ausente.
